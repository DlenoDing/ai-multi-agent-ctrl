# 管理界面与交互复验审计 Round 43

审计时间：2026-09-04 16:04 +08

## 审计范围

- 系统管理、组织管理、项目管理是否真正分层，避免同一个操作在多个管理空间重复出现。
- 系统「账号与授权」页是否仍混入项目级成员授权、Agent 注册或任务组执行控制。
- 项目「成员权限」是否已经成为项目成员角色与任务组权限落位的唯一主入口。
- 项目「AI 智能体」是否继续承载 agent 注册、一次性 join token、服务端安装脚本、远程 MCP/Skill 生效确认。
- 普通中文用户能否按“先看现状、再看操作看板、再按流程处理、最后进入表单”的顺序理解页面。

## 复验结论

前几轮已经把项目成员权限独立成项目管理页，并补齐了 Agent 注册、远程 MCP、实时回送和监控链路说明。本轮从“系统管理和项目管理是否完全分开”的角度再审，发现系统「账号与授权」页仍保留了项目成员授权表单和跳转面板。

### P1：系统账号页仍直接承载项目成员授权表单

现象：

- `renderSysAccounts()` 末尾仍渲染 `panel("项目成员授权", renderProjectMemberForm())`。
- 系统账号页操作看板里“可授权项目”仍跳到本页的“项目成员授权”面板。
- 系统账号授权流程的“项目级落位”也跳到本页的“项目成员授权”面板。

影响：

- 系统管理员会以为项目成员角色既可以在系统管理里做，也可以在项目管理里做，和“系统管理 / 项目管理完全分开”的产品规则冲突。
- 同一类项目授权存在两个入口，后续再优化项目成员权限页时容易遗漏系统页。
- 普通中文用户会把“系统账号/服务账号/跨项目授权审计”和“当前项目成员角色”混在一起。

处理方案：

- 从系统「账号与授权」页移除项目成员授权表单。
- 系统页只做账号、服务账号、访问授权审计、Agent 档案、入网令牌审计、邀请账号、新增通用访问授权、创建项目。
- 系统页所有项目成员角色落位入口统一改为跳到项目「成员权限」页；无当前项目时先引导创建或选择项目。
- 更新行为门，要求系统账号页不得再出现 `data-jump-panel="项目成员授权"`，也不得渲染项目成员授权表单；同时必须出现 `data-menu="proj-members"` 的项目级入口。

### P2：保持功能不丢失

移除的是系统页里的重复表单，不是后端能力：

- 项目成员授权能力仍在项目「成员权限」页保留。
- 系统页仍可创建项目、邀请账号、创建通用访问授权、管理 Agent 档案和审计入网令牌。
- 组织「项目列表」仍保留组织管理员视角下的项目成员授权入口。

### P3：稳定与性能

本轮不改服务端路由、不改权限模型、不改持久化结构、不新增请求。减少系统账号页的表单渲染和跨项目账号筛选，实际降低系统页认知负担与渲染内容量。

## 本轮验收要求

- 前端语法检查通过。
- 系统账号页行为门确认项目成员授权表单已经移出系统管理。
- 项目成员权限页行为门确认授权表单仍在项目管理。
- 控制台行为门、合同检查、完整验证通过。
- 本地服务与内置浏览器走查确认页面结构正确。
- 外部互审无阻断问题。
- 文档、代码和行为门全部提交并推送。
