# 管理界面第九轮多角度复验与优化方案（2026-09-03）

## 复验角度

前八轮已经把系统、组织、项目三层管理空间分离，并为账号授权、执行监控、项目设置、成员管理、智能体运行等页面补齐总览或操作看板。本轮继续从普通中文组织管理员的路径推演，重点检查“组织管理 → 项目列表”页是否还存在“只给指标和长列表，不给操作入口地图”的问题。

复验角度包括：

- 组织管理员路径：进入项目列表时，常见动作不是立即创建项目，而是先看有多少项目在用、哪些已归档、哪些健康异常、成员授权是否覆盖，再决定创建、归档或补授权。
- 中文后台习惯：高频管理页应遵循“总览 → 操作看板 → 现状列表 → 新增/授权表单”，让用户先理解现状，再做会改变组织资源边界的动作。
- 图形化入口：项目管理总览已有项目总数、在用项目、已归档、成员授权、健康异常，但这些只是数字，不是可点击的管理入口。
- 操作闭环：项目列表、创建项目、项目成员授权是同一条组织项目管理链路，应在总览后形成可跳转入口，避免用户在长页面中查找。
- 信息完整性：不删除项目列表、创建项目、项目成员授权、归档操作和现有指标。
- 性能边界：只用当前 `state.projects` 和已加载成员数据聚合，不新增接口、不增加轮询、不引入依赖；继续复用 `jumpModuleCard` 与 `data-jump-panel`。

## 发现的问题

- 「组织管理 → 项目列表」页当前顺序是“项目管理总览 → 项目列表 → 创建项目 → 项目成员授权”。顺序比早期版本更合理，但总览和长表之间缺少操作看板。
- 用户看到“健康异常 1”“已归档 2”“成员授权 5”后，不能直接跳到项目列表或授权表单，只能继续向下读页面。
- 创建项目和项目成员授权都是改变组织资源边界的操作，应该在用户核对项目列表后再执行；页面需要更明确地表达这个处理顺序。
- 与账号授权页、执行监控页、项目设置页相比，组织项目页的图形化入口能力不一致，降低了整套后台管理的一致性。

## 优化方案

- 新增“项目管理操作看板”，放在“项目管理总览”之后、“项目列表”之前。
- 看板卡片覆盖：在用项目、健康异常、已归档项目、成员授权、创建项目、补成员授权。
- 在用项目、健康异常、已归档项目、成员授权卡片跳转到“项目列表”；创建项目跳转到“创建项目”；补成员授权跳转到“项目成员授权”。
- 看板说明固定处理顺序：先核对项目状态与成员覆盖，再创建项目、归档项目或补授权。
- 补充行为门，断言组织项目页必须先显示总览和操作看板，再显示项目列表、创建项目、项目成员授权，并断言看板跳转目标存在。

## 验收要求

- 桌面页面：组织项目页先显示项目管理总览、项目管理操作看板，再显示项目列表、创建项目、项目成员授权。
- 移动端页面：390px 宽度下新增操作看板不造成页面级横向溢出。
- 工程验证：语法检查、diff 卫生、console-behaviour-gate、mutation-anchors、validate、docker:doctor 通过。
- 运行验证：本地服务启动后用真实浏览器登录组织项目页，检查看板可读性、卡片跳转和窄屏表现。

## 实施结果

- 已新增“项目管理操作看板”，覆盖在用项目、健康异常、已归档项目、成员授权、创建项目和补成员授权。
- 已复用既有 `jumpModuleCard` 与 `data-jump-panel` 跳转机制，不新增接口、不新增轮询、不引入依赖。
- 已将组织项目页顺序调整为“项目管理总览 → 项目管理操作看板 → 项目列表 → 创建项目 → 项目成员授权”。
- 已补充行为门断言，使用真实整页渲染入口验证组织项目页先显示总览和操作看板，再显示列表、创建项目和成员授权，并确保看板卡片带有项目列表、创建项目和项目成员授权跳转目标。
- 已完成快速工程验证：语法检查、diff 卫生、console-behaviour-gate 和 mutation-anchors 通过。
- 已完成真实浏览器边界复验：本地 seed 运行态中系统管理员只显示系统管理入口，项目负责人只显示项目管理入口，均不能直接看到组织项目页，符合系统/组织/项目空间分离要求。
- 本轮未为了浏览器复验临时创建组织管理员账号，避免污染本机 `.runtime` 运行态；组织项目页 DOM 结构、顺序和跳转目标由 console-behaviour-gate 的真实整页渲染夹具覆盖。
