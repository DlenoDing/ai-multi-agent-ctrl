# 管理界面第六轮多角度复验与优化方案（2026-09-03）

## 复验角度

前几轮已经完成系统管理、组织管理、项目管理的空间分离，并给项目概览、系统设置、成员管理、智能体、人工审核、人工指令等高密度页面补上总览。本轮继续从普通中文管理者的真实阅读路径推演：打开页面后，能不能先知道“现在该盯哪里”，再进入表单、长表和底层执行记录。

复验角度包括：

- 管理优先级：任务组和监控页面不应只给总数，还应把需要先处理的对象排出来。
- 操作路径：用户看到问题后，应能直接跳到对应任务组或对应明细面板，不靠记住页面结构。
- 信息完整性：原有执行事件、派发、会话、节点、关闭门禁、质量门禁、规则处置等信息全部保留。
- 中文习惯：先给“处置看板 / 问题看板”，再给创建表单和明细表；避免首屏先让用户填东西。
- 性能边界：新增看板只基于页面已经加载的集合做 O(n) 聚合，不新增接口、不扩大轮询、不引入框架。

## 发现的问题

- 「任务组」页已有任务组总览，但总览之后直接进入“创建任务组 / 创建工作项”表单。对于已有任务组的项目，普通用户更需要先看到哪些任务组需要关注、哪些在运行、哪些可关闭或已关闭，而不是先被推去创建新对象。
- 任务组列表每个任务组都作为一个大面板展示，信息完整但排序和优先级不明显。用户需要逐个读卡片，才能判断哪个组因为关闭门、派发阻塞、工作项阻塞、无在线 agent 或人工待办而需要先处理。
- 「执行监控」页已有总览，但下面仍是大量明细表。用户知道“有阻塞”之后，仍要在实时事件、派发、会话、控制通道、死信、节点、关闭门、质量门之间来回找入口。
- 监控页没有一张把“先处理什么”聚合出来的处置看板，尤其是派发阻塞、未满足关闭门、卡住的执行方案、失败测试、异常节点这些对象本来属于不同表，却都可能影响任务组推进。

## 优化方案

- 新增“任务组处置看板”：按任务组聚合关闭门阻塞、派发阻塞、工作项阻塞、无在线 agent 但已有交付中工作项、待人工确认、当前进度和统一语言，优先展示需要关注的任务组。
- 任务组看板卡片直接复用任务组详情展开动作，用户点击卡片即可展开相应任务组，不需要再到长列表里寻找。
- 新增“监控处置看板”：把执行监控页的关键问题聚合为“派发阻塞、关闭门禁、执行方案、质量/测试、节点、自主管理”六类，并提供跳转到对应明细面板的按钮。
- 为监控看板增加面板跳转交互：点击看板卡片后滚动到对应明细面板，保留原有表格与过滤器。
- 补充行为门：断言任务组页必须按“任务组总览 → 任务组处置看板 → 创建任务组”展示，监控页必须按“执行监控总览 → 监控处置看板 → 实时事件流”展示，并验证监控看板的跳转按钮存在。

## 验收要求

- 桌面页面：任务组页先出现总览和处置看板，再出现创建表单；监控页先出现总览和处置看板，再进入实时事件与明细表。
- 移动端页面：390px 宽度下新增看板不造成页面级横向溢出。
- 工程验证：语法检查、diff 卫生、console-behaviour-gate、mutation-anchors、contract:check、validate、docker:doctor 通过。
- 运行验证：本地服务启动后用真实浏览器登录项目管理页，检查任务组与执行监控页面的首屏顺序、卡片可读性和跳转可用性。

## 实施结果

- 已新增“任务组处置看板”，在任务组总览之后、创建表单之前展示，并按关闭门阻塞、派发阻塞、人工待办、工作项阻塞、无在线 agent 等信号排序。
- 任务组看板卡片已接入既有“查看详情”动作，点击即可展开对应任务组，不新增后端接口。
- 已新增“监控处置看板”，把执行监控中的派发/会话、关闭门禁、执行方案、质量/测试、节点、自治周期六类问题先聚合成卡片。
- 监控看板卡片已接入面板跳转，点击后滚动到对应明细面板；无对应明细时给出提示，不静默失效。
- 已补充行为门断言，确保任务组页和执行监控页后续不会退回到“总览后直接表单/长表”的结构。
- 已完成快速工程验证：语法检查、diff 卫生、console-behaviour-gate 和 mutation-anchors 通过。
