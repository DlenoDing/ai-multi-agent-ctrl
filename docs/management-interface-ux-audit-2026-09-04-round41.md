# 第四十一轮管理界面与项目成员权限复验

## 复验范围

本轮继续按普通中文用户的真实管理路径复验系统管理、组织管理、项目管理、任务组、执行监控、人工审核、人工指令、项目设置和 Agent 管理。前几轮已经把 Agent 注册、节点处置、仓库产出、规则治理等高密度内容拆出总览、看板和流程。本轮重点检查项目内部是否仍缺少关键管理入口。

## 多角度复验结论

1. 系统管理和组织管理已经保持独立：系统侧负责组织、账号、全局设置和跨项目审计；组织侧负责成员生命周期、组织级 Agent 审计和项目列表。
2. 项目管理已经覆盖项目概览、AI 智能体、任务组、执行监控、人工审核、人工指令和项目设置。
3. Agent 注册链路已经明确落在项目“AI 智能体”页：一次性 join token 由服务端签发，注册脚本由服务端生成，MCP 服务集中在控制面。
4. 项目设置页已新增规则治理概览，避免用户直接进入长系统规则正文。
5. 项目成员授权仍没有项目侧独立入口，只能在组织“项目列表”或系统“账号与授权”页中的“项目成员授权”表单完成。

## 发现的问题

### P1：项目成员和权限不应只藏在组织/系统页面

项目成员授权决定谁能管理项目、谁能操作 Agent、谁能控制任务组、谁能做人工审核。当前实现中，“项目成员授权”表单存在，但不在项目管理菜单内。普通项目负责人进入某个项目后，能看到任务组、Agent、监控和设置，却不能在同一项目空间里直接查看本项目成员角色和授权入口。

影响：

- 用户需要先知道授权表单藏在组织“项目列表”或系统“账号与授权”页，路径不符合中文用户“先进入项目，再管理项目内成员”的操作习惯。
- 项目概览里的“项目设置”卡片说明了“授权边界”，但点进去后仍只有仓库、规则、默认角色和 Skill 定制，没有成员权限面板。
- 当执行监控或人工审核提示“需要项目成员授权”时，用户缺少一个项目侧主菜单入口可直接回到本项目授权。

### P2：优化必须保持简单、稳定和高性能

本轮不新增后端接口、不改变权限模型、不改变成员授权写路径。只在前端项目菜单中新增“成员权限”页面，复用当前状态里已经下发的项目成员、账号和现有 `renderProjectMemberForm()` 写路径。页面只做当前项目的成员与角色展示、授权流程说明和授权表单入口。

## 改进方案

1. 在项目管理菜单中新增“成员权限”，放在“项目概览”之后、“AI 智能体”之前。
2. 新页面展示本项目成员总数、项目管理员、任务组负责人、评审人、智能体操作员和观察者数量。
3. 新页面提供图形化流程：组织成员入网 → 项目角色授权 → 任务组/审核/Agent 页面出现对应按钮 → 后续在执行监控回看。
4. 新页面列出当前项目成员与角色，不把用户带回组织全局列表才能理解本项目授权现状。
5. 新页面保留现有“项目成员授权”表单，但默认聚焦当前项目，不新增服务端写路径。
6. 补充控制台行为门，固定项目菜单顺序、页面总览、流程、成员表和授权表单。

## 已实施

1. 项目管理菜单新增“成员权限”，放在“项目概览”之后、“AI 智能体”之前。
2. 项目概览新增“成员权限”入口卡片，并把“项目操作路径”调整为：权限落位 → 执行准备 → 任务组织 → 实时监控 → 人工介入 → 控制补充 → 配置调整。
3. 新增项目“成员权限”页，包含成员权限总览、成员权限操作看板、成员协作流程、项目成员列表和项目成员授权。
4. 成员权限页按当前项目统计项目管理员、任务组负责人、评审人、智能体操作员和观察者。
5. 项目内授权表单复用现有 `/api/projects/:id/members` 写路径，但锁定当前项目，避免用户在项目页误切到别的项目授权。
6. 项目成员页只在当前账号具备 `project:grant` 时加载组织成员目录；只读查看成员角色时不额外请求成员列表，减少高并发下无意义的接口压力。
7. 勘察工具、项目级取数判据、菜单顺序判据和控制台行为门均已纳入 `proj-members`。

## 复审结论

本轮改动没有新增后端状态、接口或轮询，也没有改变权限模型。成员授权仍由原服务端守卫、幂等键和审计链路处理；前端只把本项目成员权限变成项目空间内的一等管理入口。系统管理、组织管理和项目管理的职责边界保持分离：组织页仍处理账号生命周期，项目页处理当前项目成员角色与执行权限落位。
