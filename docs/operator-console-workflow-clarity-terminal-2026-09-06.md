# 中文管理控制台流程清晰度终态审计

日期：2026-09-06  
状态：已完成并通过终态复验

## 本轮审计方法

不以“已经有 Tab 或菜单”为完成标准，而以普通管理者能否从稳定入口连续完成一个对象的列表、创建、详情、授权、监控和处置为标准。逐项对照 `navigation.js` 的可见入口、`workspaces.js` 的面板所有权、真实账号权限和浏览器页面。

## 已确认边界

- 系统管理员只进入系统治理空间，只管理组织、初始组织管理员、配额、启停和平台能力。
- 组织管理员管理组织子账户、组织项目目录、项目／任务组授权、组织共享 Agent 档案和共享运行节点。
- 项目空间同时展示当前项目 Agent 与本组织共享 Agent，任务组调度已通过真实 e2e 验证两类候选的作用域和跨组织排除。
- 项目、任务组和任务均有独立进度；任务列表按时间倒序，任务详情包含执行尝试、Agent、角色、模型、规则、事件和 Git 结果。
- 项目级与任务组级监控共用同一执行数据链，任务组范围进入页头、地址、查询和权限判断。

## 第一项剩余问题：成员授权仍是复合页面

`项目成员` pane 同时拥有“项目成员列表”和“项目成员授权”；`任务组权限` pane 同时拥有“任务组权限列表”和“任务组权限授权”。这仍是把查阅与创建表单放在一页，只是外面换了菜单名。

终态拆分为四个稳定入口：

1. 项目成员：只看成员、角色影响和成员详情。
2. 添加项目成员：只选择组织账号与项目角色并提交。
3. 任务组权限：只看按任务组分配的角色和状态。
4. 授予任务组权限：只选择任务组、账号和任务组角色并提交。

无 `project:grant` 权限的账号不显示两个授权入口；列表和详情仍可按其读取权限访问。四个入口使用独立 `pane` 地址，列表页按钮直接进入创建页，不再在长页面内滚动定位表单。

## 第二项剩余问题：执行对象仍堆在“执行会话”

原“执行会话”页面同时渲染工作会话、Agent 派发、Worker Lane、模型选择和会话放置五类对象。它们的排障问题不同：会话回答是否持续、派发回答任务交给谁、Lane 回答载体复用、模型决策回答为何选这个模型、会话放置回答为何新建会话或使用子 Agent。

现拆为“工作会话、Agent 派发、执行载体、模型决策、会话放置”五个稳定入口；任务组范围进入后显示对应的任务组级标题。旧 `pane=runs` 地址自动迁移到“工作会话”，节点的“当前任务”入口直达“Agent 派发”。

## 第三项剩余问题：节点、命令和死信混在一起

原“节点控制”同时展示运行节点、控制命令 ACK 和死信队列。现拆为“运行节点、控制命令、死信队列”三个入口：先看节点健康和准入，再看控制命令是否送达／确认，重试超限才进入死信处置。旧 `pane=nodes` 地址自动迁移到“运行节点”。

## 第四项剩余问题：产出、质量与裁决混在一起

原“产出验收”同时展示 Git 检查点、质量门／测试证据和人工定稿记录。现拆为“检查点证据、质量门禁、人工定稿”三个入口；质量门待办和项目当前主操作直达“质量门禁”。旧 `pane=evidence` 地址自动迁移到“检查点证据”。

## 第五项剩余问题：放置与准入混在一起

会话放置决定使用新会话、已有会话或子 Agent；准入决策记录阶段门、容量和依赖为什么允许／拒绝执行。现拆为“会话放置”和“准入决策”两个入口，避免把执行载体选择误读成准入结论。

## 第六项剩余问题：三类人工处置混在一起

原“授权与复核”把权限请求、危险操作审批和评审发现混在同一页。现拆为“权限审批、操作审批、发现处置”：权限审批显示主体、权限和资源作用域；操作审批处理危险动作和阶段门；发现处置要求结论、状态与必要证据。待办红点和项目主操作按实际类别直达对应页面，多类别同时存在时进入待办汇总。旧 `pane=decisions` 地址迁移到“权限审批”。

## 第七项剩余问题：默认角色与 Skill 覆盖混在一起

项目默认角色决定任务组未指定时的角色回退；角色 Skill 定制改变项目／任务组的能力和约束。现拆为“默认角色”和“Skill 定制”两个项目治理入口，旧 `pane=roles` 地址迁移到“默认角色”。

## 第八项剩余问题：指令效率、信封与共享定义混在一起

指令压缩指标用于观察 token 和缓存命中；指令信封用于查看固定 envelope、接收角色、缓存键和目标 token；共享定义归属用于确定多子项目公共标准由谁定义、产出和裁决。现拆为“指令效率”“指令信封”和“共享定义”三个系统能力入口，旧 `pane=protocol` 地址迁移到“指令效率”。

## 第九项剩余问题：阻塞处置与关闭门混在一起

需要真人收尾的评审计划、规则来源、共享定义和卡住方案属于操作队列；关闭门属于任务组是否可终结的计算结果。现拆为“阻塞处置”和“关闭门禁”，待办与项目主操作直达阻塞处置。旧 `pane=barriers` 地址迁移到“阻塞处置”。

## 第十项剩余问题：系统界面跨入用户 Agent 配置

系统设置曾展示全平台项目／任务组的角色 Skill 叠加明细，这属于用户项目和 Agent 配置，不符合系统管理员只管理组织治理与平台能力的边界。系统页面现只保留技能源本身；项目 Skill 覆盖在项目“Skill 定制”和任务组详情中查看、创建和审计。系统设置总览也移入说明页，运行参数页只显示运行参数。

## 第十一项剩余问题：执行观测菜单自身过长

监控对象拆分后，原“执行观测”分组一次展开十多个叶子。现按任务语义分成“执行跟踪、节点与控制、验收与收口”三组：前者回答执行到哪，第二组处理执行载体与命令，第三组处理证据、质量、裁决、阻塞和关闭。

## 第十二项剩余问题：任务组详情仍是复合配置页

原“角色与规则”栏目把实际参与角色、配置继承、默认角色、Skill 定制、系统规则和业务规则混在同一页；规则量大时，普通管理者无法快速确认自己正在修改哪一层。现将任务组对象栏按“工作推进、执行配置、控制与追溯”分组，并把参与角色、配置继承、Skill 定制、系统规则、业务规则分别设为独立栏目。事项拆解、执行时间线、准入与阻断、阻塞处置也分别拥有稳定入口。

同时修复详情阅读卡的路由作用域：任务组详情内的卡片现在按 `group-detail` 对象局部栏目解析目标，不再错误地按父级 `tg` 页面跳转。旧 `pane=config` 地址自动迁移到“配置继承”。

## 第十三项剩余问题：项目设置卡片与失败状态归属错误

项目设置说明页中的“基线数据”和“默认角色”卡曾统一跳到仓库页；配置接口失败时，系统规则与业务规则两个独立栏目又没有错误内容，失败提示只归在仓库页。现按稳定功能页重新接线：仓库、基线、默认角色、Skill、系统规则和业务规则卡分别直达对应栏目；系统规则与业务规则在配置读取中和读取失败时分别显示自己的安全空态，规则编辑器仍保持隐藏以防误保存清空规则。

## 第十四项剩余问题：项目设置视图继续堆在主程序

项目设置的总览、操作看板、职责分区、生效流程和规则治理概览原本都由 `app.js` 直接生成。现迁入独立 `project-settings-workspace.js`，主程序只提供当前项目快照、权限结果和通用渲染依赖；浏览器与行为门按相同脚本顺序加载该模块。此拆分不改变 API、表单字段、配置版本锁或保存路径。

任务组详情的十二项图形化阅读路径也迁入既有 `task-group-insights.js`，与该模块已经负责的执行时间线和监控矩阵放在同一领域边界内；主程序不再保留第二份模板。

## 第十五项剩余问题：系统能力页仍跨入项目治理

系统设置虽已移除角色 Skill 叠加明细，但总览、操作看板和治理流程仍汇总项目／任务组叠加数量，并给系统管理员展示无法进入的“项目设置”“Agent 注册”卡。现彻底移除这些用户项目数据与死入口，系统空间只保留运行参数、模型能力、技能源、指令效率、指令信封和共享定义。项目级 Agent 与 Skill 定制仍只在组织／项目空间管理。

## 第十六项剩余问题：成员详情对已有项目角色仍显示通用授权

真实以组织管理员查看项目负责人时，成员详情仍展示“分配项目角色”表单，但候选账号里不会出现当前成员，形成一张看得见却无法用于当前对象的表单；任务组授权又允许在成员甲详情里改选成员乙。现将项目选择明确命名为“当前管理项目”：成员尚未加入该项目时显示已锁定当前成员的定向授权表单；已有项目角色时显示现有角色和“管理项目角色”入口，不再混入面向其他成员的通用授权。任务组授权也固定当前成员，只允许选择任务组和角色。

## 第十七项剩余问题：任务组详情模板仍挤在主程序

任务组详情的事项、角色、配置、Skill、规则、控制、任务执行历史、阻塞和协作记录约 300 行模板现整体迁入 `task-group-detail-workspace.js`。模块只消费控制面已经加载并裁剪过的快照，不自行请求接口或修改状态；`app.js` 继续负责权限事实、提交处理和实时数据装配。行为门的视图字段扫描同步扩大到浏览器实际加载的全部模块，并为任务详情事件索引补上与服务端 60 条账本窗口一致的显式上限。

## 第十八项剩余问题：核心门面混入完整命令总线状态机

`control-plane-core.mjs` 内原有约 370 行 Command、CommandEffect、DLQEntry 生命周期。现迁入 `command-bus.mjs`，由核心门面注入集合初始化、转移记录、审计事件、摘要和输入校验依赖，再按原名称重新导出。服务端、MCP 与测试导入路径不变；命令超时、重试、效果对账、死信人工处置和关闭门语义均保持原契约。全局时间字段、白名单拒绝、i18n 来源与容量裁剪元检查同步纳入新模块。

## 第十九项剩余问题：运行问题收集与核心编排混放

运行问题样本、重复模式、升级候选和候选处置传导现迁入 `runtime-issue-tracker.mjs`。模块继续执行 `collect_only` 策略，只生成供系统外独立维护使用的候选；不会修改活动规则、调度策略、权限、MCP grant 或自行创建升级任务组。核心门面保持 `collectRuntimeIssue` 与 `settleRuntimeIssuePatternForCandidate` 兼容导出。

## 第二十项剩余问题：完整执行监控仍由单个主函数渲染

会话、派发、Lane、节点、控制命令、模型决策、放置、准入、实时事件、检查点、质量、阻塞和关闭门原由 `app.js` 内一个约 540 行函数生成。现整体迁入 `monitor-dashboard-workspace.js`；主程序只传入当前项目／任务组作用域、实时分页状态、权限结果和稳定 helper。浏览器、界面门与契约门均从 `index.html` 的真实脚本清单识别模块，表格截断、百分比缺省、按组判权、定稿理由和阻塞出口等既有守卫继续生效。

首次全新浏览器复验发现迁移时漏传 `execEventsDropped`，切换监控后 URL 已变化但页面因异常停留在旧内容。现已补齐上下文，并新增“模块声明的每个运行时上下文键都必须由主程序传入”的结构门与变异；两套浏览器审计随后重新全绿。

## 第二十一项剩余问题：拆分后验证门仍只扫描历史单文件

全量验证暴露出 Ruby 规范门和部分 Node 契约门仍只扫描 `app.js`／`control-plane-core.mjs`，会把已迁出的真人杠杆、监控证据、状态裁剪和错误码误判为缺失，也会让后续模块回归逃逸。现统一从 `index.html` 提取真实前端脚本，并将核心门面、Command Bus、运行问题追踪纳入领域产品源码；逐文件精确断言仍保留原边界。

同轮活性检查发现 `DerivedTaskRequest` 规范声明候选、强化、分类、吸收四段状态，实际拆分记录却直接写成终态。现于人工定稿后的同一原子编排事务内走完三条合法转移并留下证据，再落为 `absorbed`；关闭门不再依赖从未产生的状态。工厂返回／门面重导出也不再被死导出检查误当成生产调用。

## 第二十二项剩余问题：完整变异门中的七条判据随拆分失效

首次 1571 条完整变异运行发现七条假绿／错因红：成员与 Agent 指引、配置加载三态和待办叶子的期望文案已过时；任务组剥离字段与监控双视图接线仍只扫描主文件；Command Bus 工厂返回和门面重导出被误计为产品调用。现逐条修正，七条变异已分别重跑并以预期原因报红，基线门保持全绿。

## 第二十三项外部互审：事件窗口与核心扫描清单

Claude Sonnet/medium 以只读模式审查 `a82eeeb..HEAD` 后提出两项 P2，逐项复核均成立：

1. 任务详情接口以时间升序返回最新 120 条事件，二次 `slice(0, 60)` 会保留窗口中最旧的一半。现改为 `slice(-60)`，当前派发事件与派发快照已淘汰的历史事件均新增 120 条升序夹具，证明只保留最新 60 条；方向回退与取消上限各有独立变异。
2. 白名单拒绝、调用方时间、调用方对象展开和容量裁剪四类核心元检查已纳入 `command-bus.mjs`，但漏了同批新增的 `runtime-issue-tracker.mjs`。现四处全部补齐，虽然当前模块没有对应违规，后续新增调用方字段或裁剪函数时不会从扫描面逃逸。

Claude Opus/high 的第一次全仓只读审查运行约 11 分钟未返回结论，已终止且未采信；随后收窄差异范围的 Sonnet 审查完成并给出上述可复核结论。

修复后第二轮 Claude Sonnet/medium 只读复核确认两项均无问题，并实际运行 823 条界面断言与 277 条契约检查。其附带怀疑 `task-group-insights.js` 的 `slice(0, 60)` 同类反向，经复核不成立：该模块读取的是中央状态视图，唯一生产者 `recordAgentExecutionEvent` 使用 `unshift`，数组顺序为最新在前；任务详情读取的则是项目事件接口，该接口显式按 sequence 升序，两处数据源顺序不同，不能统一改成 `slice(-60)`。

## 2026-09-07 追记：按从属层级收敛（覆盖上文「每个对象一个稳定入口」的做法）

用户看过上文终态后的判断：入口多、到处交叉、认知杂乱；要求所有栏目按「项目 → 任务组 → 任务」的从属层级收敛，不为管理而展示。收敛后的形态（以此为准，上文各「拆成独立页面」的条目作废）：

### 2026-09-07 晚 真实执行走查：产出目标被劫持到控制面自己的仓库

接着首次开通走查，给同一个新项目注册了一台本机运行节点、真的让任务跑起来。第一次执行就暴露了一个后端缺陷，

「项目设置」里登记的仓库只在服务端没有 origin 时才用。控制面从 git 检出目录里起来时，所有项目的产出目标都
被改指到控制面自己的远端、基准提交是控制面的 HEAD、白名单是控制面的目录布局 —— 这台节点把示例产出直接推到了
控制面仓库的 main（已 revert）。同一条路上还有一处：校验检查点前对项目仓库的 fetch 不带项目登记的凭据，私有仓库
的检查点会一直「commit 找不到」。

修正（契约门两条新断言、五条红证过的变异）：
- 只有自管项目（没登记仓库，或登记的就是 repo_control_plane 那份自检仓）才由服务端工作区推导；其余按登记仓库
  取地址、默认分支，基准留空（校验按 finalCommit^ 比对，agent 按 origin/<branch> 起分支），白名单登记里没写就整仓可写；
  人改了仓库地址后，未推送的既有目标跟着改。
- 校验 fetch 用与「测试连接」同一套隔离 askpass 环境带上认领时投递的那份凭据，用完即删。

同一屏上顺手修的界面：原因码链逐段翻译并去掉末尾 HTTP 状态（原先只翻第一段）；卡住的任务结果标题不再写
「正在生成仓库产出」；待决策／反复失败的出口提示直接带一个预选好任务组与任务的「去人工指令处置这个任务」入口；
三张对象页头程序聚焦不再画蓝框（键盘聚焦仍有）。
- 修完再跑又撞两处：agent 运行时自己的白名单匹配只认 dir/** 与逐字，控制面给项目仓库缺省发的 `**` 被判越界（三次派发全失败）——
  运行时改成与 path-policy 同一套通配语义，契约门拿同一张表两端逐条比对；人工指令「重开」只把工作项置回就绪、受阻的旧派发留着，
  编排一直复用旧契约永不再派——重开先了结上一次尝试的派发／会话／租约／产出目标，下一拍按当前登记的仓库重建。
