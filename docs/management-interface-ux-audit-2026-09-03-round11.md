# 管理界面第十一轮多角度复验与优化方案（2026-09-03）

## 复验范围

前十轮已经补齐系统组织、系统账号、系统设置、组织项目、项目设置、任务组、执行监控等高密度页面的总览和图形化入口。本轮继续从中文用户的日常管理动作推演，重点检查项目空间内“人工指令”页是否还存在“指标有了，但没有操作路径地图”的问题。

复验角度包括：

- 中文后台习惯：项目级控制页应先告诉用户“当前有没有待处理、拒绝、可控范围”，再让用户读流水或提交新指令。
- AI-native 执行边界：人工指令不是直接改总控会话，而是进入编排输入；页面需要突出“先查流水，再决定是否下达”的机器执行闭环。
- 图形化入口：人工指令总览已有指令总数、待处理、已执行、已拒绝、涉及任务组、可控任务组，但这些指标还不能直接跳到指令流水或下达入口。
- 重复操作风险：如果用户没先看到已有指令是否已执行或被拒，容易重复下达相同控制意图。
- 信息完整性：不减少指令流水、拒绝原因、已执行动作、下达表单和权限提示。
- 性能边界：只基于当前已加载的指令列表和任务组聚合，不新增接口、不新增轮询、不引入依赖；继续复用 `jumpModuleCard` 与 `data-jump-panel`。

## 发现的问题

- 「人工指令」页当前顺序是“人工指令总览 → 指令流水 → 下达人工指令”，比早期表单优先的结构已经更合理，但仍缺少总览后的图形化操作入口。
- 用户看到“待处理”“已拒绝”“可控任务组”等数字后，不能直接按问题类型进入流水或表单，只能继续向下读长表。
- 与账号授权、组织项目、系统组织、项目设置和执行监控页相比，人工指令页缺少同形的入口地图，项目控制区的交互一致性不足。
- 人工指令是影响总控和调度的高风险输入，应更明确表达处理顺序：先核对流水，再下达新指令。

## 优化方案

- 新增“人工指令操作看板”，放在“人工指令总览”之后、“指令流水”之前。
- 看板卡片覆盖：待处理、已拒绝、已执行、涉及任务组、可控任务组、下达入口。
- 待处理、已拒绝、已执行、涉及任务组卡片跳转到“指令流水”；可控任务组和下达入口卡片跳转到“下达人工指令”。
- 看板说明固定处理顺序：先核对待处理、拒绝原因和已执行动作，再下达新指令。
- 补充行为门，断言人工指令页必须先显示总览和操作看板，再显示流水和下达表单，并断言看板跳转目标存在。

## 验收要求

- 桌面页面：人工指令页先显示人工指令总览、人工指令操作看板，再显示指令流水和下达人工指令。
- 移动端页面：390px 宽度下新增操作看板不造成页面级横向溢出。
- 工程验证：语法检查、diff 卫生、console-behaviour-gate、mutation-anchors、validate、docker:doctor 通过。
- 运行验证：本地服务启动后用真实浏览器登录人工指令页，检查看板可读性、卡片跳转和窄屏表现。

## 实施结果

- 已在 `apps/control-plane-ui/public/app.js` 新增“人工指令操作看板”，放在“人工指令总览”之后、“指令流水”之前。
- 已抽出 `directiveStats`，让总览和操作看板共用同一套统计口径，避免待处理、已拒绝、已执行、涉及任务组和可控任务组数字不一致。
- 看板复用现有 `jumpModuleCard`，不新增接口、不新增轮询、不新增依赖；所有指标均来自当前项目已加载指令列表和任务组。
- 已补充 `scripts/console-behaviour-check.mjs` 行为门，覆盖人工指令页的面板顺序和看板跳转目标。
- 已通过 `node --check apps/control-plane-ui/public/app.js`、`node --check scripts/console-behaviour-check.mjs`、`git diff --check`、`npm run console-behaviour-gate`、`npm run mutation-anchors`。
- 真实浏览器桌面走查通过：人工指令页显示 4 个面板，顺序为“人工指令总览 → 人工指令操作看板 → 指令流水 → 下达人工指令”；看板 6 张卡片均有明确跳转目标；页面无横向溢出。
- 真实浏览器交互走查通过：点击“指令流水”和“下达人工指令”卡片后，对应面板进入当前视口。
- 真实浏览器 390px 窄屏走查通过：看板仍为 6 张可读卡片，页面级 `scrollWidth` 与视口宽度一致；导航区域局部横向滚动不撑开整页。
