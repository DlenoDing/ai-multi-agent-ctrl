# 管理界面与交互复验审计 Round 42

审计时间：2026-09-04 15:44 +08

## 审计范围

- 系统管理、组织管理、项目管理三层入口是否继续保持职责分离。
- 项目「成员权限」上线后，任务组、执行监控、人工审核、组织成员、系统账号页的跨页面指引是否一致。
- Agent 注册、一次性 join token、远程 MCP、Skill 同步是否仍然明确指向项目级 AI 智能体页，避免用户到系统账号或项目设置页寻找注册脚本。
- 普通中文用户能否在权限不足、节点不可用、任务组无法关闭等异常场景中快速理解“去哪里处理、找谁处理、处理什么”。
- 本轮仅做低风险界面与行为门优化，不改数据模型、不改服务端协议、不扩大实时链路实现面。

## 复验结论

系统主结构相比前几轮已经明显分层：系统管理负责平台级账号、模型、集中 MCP、技能源；组织管理负责组织成员生命周期、项目列表和组织级 Agent 治理；项目管理负责成员权限、AI 智能体、任务组、监控、审核、指令和项目设置。当前仍发现一个影响中文用户理解成本的问题。

### P1：项目级成员权限页上线后，部分指引仍停留在旧入口称呼

现象：

- `requestFailureHint()` 在任务组权限缺失时仍提示“只能在「项目成员授权」里按角色授予”，没有说明它现在位于「项目管理」→「成员权限」→「项目成员授权」。
- 执行监控的关闭门阻塞提示也只写“项目成员授权”，用户从监控页看到后需要自己猜它属于哪个菜单。
- 组织成员页的流程图仍把项目授权描述为「组织管理」→「项目列表」→「项目成员授权」，没有把新项目级「成员权限」作为优先入口。
- 组织成员页的底部闭环仍写“项目成员授权”，没有明确“进入目标项目的成员权限页授权”。

影响：

- 新用户更容易把系统账号权限、组织成员权限、项目成员角色混为一谈。
- 权限不足类错误虽然能说出缺哪个权限，但没有直接指到新菜单，降低了处理效率。
- 监控角色发现任务组无法关闭时，人侧处置链路不够短，容易在系统管理或组织成员页来回查找。

处理方案：

- 将权限缺失、关闭门阻塞、组织成员流程、组织成员说明里的授权指引统一改为“优先进入目标项目「成员权限」→「项目成员授权」；组织项目列表保留集中入口”。
- 保留“项目成员授权”作为具体面板名，避免丢失已有功能定位。
- 更新行为门，要求相关页面必须同时出现“项目管理”“成员权限”“项目成员授权”等关键路径。

### P2：保持简单、稳定和性能

本轮不新增 API、不新增持久化字段、不引入新的前端状态订阅。改动集中在用户可见文案和控制台行为门：

- 简单：只修正跨页面路径语义。
- 稳定：不触碰服务端授权判定、实时通道、数据库隔离、Agent 注册协议。
- 性能：不增加任何请求；项目成员页仍只有在具备 `project:grant` 时才读取组织成员目录。

## 实施结果

- 任务组权限拒绝提示已改为指向「项目管理」→「成员权限」→「项目成员授权」，并继续说明直接写在账号上的任务组权限不生效。
- 组织成员创建页的任务组权限说明已改为项目级成员权限入口，不再把系统账号页描述成项目任务组授权入口。
- 组织成员授权流程已按项目上下文分流：
  - 已选择目标项目时，“分配项目”卡片直接进入项目「成员权限」页。
  - 没有目标项目时，仍回「组织管理」→「项目列表」先选项目。
- 执行监控里关闭门阻塞的“你处置不了”提示已改为完整路径，避免只给“项目成员授权”面板名。
- 控制台行为门新增/收紧 3 条断言：
  - `requestFailureHint()` 的任务组权限拒绝必须出现完整项目成员权限路径。
  - 监控页按任务组判权的阻塞提示必须出现完整项目成员权限路径。
  - 组织成员授权流程必须在有/无当前项目两种状态下分别指向正确入口。
