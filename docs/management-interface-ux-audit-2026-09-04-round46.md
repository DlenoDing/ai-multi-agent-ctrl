# 管理界面与控制链路复验调整清单（round46）

检查时间：2026-09-04

## 结论

当前控制台已经把系统、组织、项目做了初步空间切换，但边界仍不够严格：系统管理里还保留了账号授权、逻辑 Agent、系统级项目创建等日常租户操作；组织成员页没有直接展示子账户在项目和任务组上的权限矩阵；项目仓库仍以环境变量凭证引用为主；Agent 的组织级和项目级作用域在界面上没有形成清晰档案；任务执行详情还需要更直观地串起“工作项、会话、派发、模型、规则、事件、结果”。

这些问题会降低中文用户的认知效率，也会让 AI-native 执行系统的核心管理边界变模糊。终态应按“系统开通组织、组织管理资源、项目管理执行、任务组管理过程”的层级呈现。

## 必须修正

1. 系统管理边界
   - 系统管理只保留组织、配额、组织启停、初始组织管理员账号和平台运行设置。
   - 移除系统菜单中的“账号与授权”入口，避免系统管理员日常代替组织管理员管理子账户、Agent 和项目。
   - 组织列表补充初始组织管理员账号、子账户用量、项目用量、任务组用量、Agent 用量。

2. 组织成员与权限
   - 组织管理员需要能看清每个子账户当前拥有哪些组织权限、项目角色和任务组角色。
   - 组织成员页增加项目/任务组权限矩阵，项目级或任务组级授权入口指向项目“成员权限”页。
   - 组织账号生命周期和项目协作权限必须分开解释，避免把组织权限误读为任务执行权限。

3. 项目成员与任务组权限
   - 项目“成员权限”页不仅要能授项目角色，也要能按具体任务组授予任务组负责人、评审人、智能体操作员、观察者等权限。
   - 页面需要展示当前项目下任务组授权列表，便于人工复核谁能控制、审核或观察哪个任务组。

4. 仓库访问配置
   - 项目仓库不能继续只填 `env:` 凭证引用。不同组织和项目的仓库不同，凭据必须作为项目仓库配置的一部分由服务端管理。
   - 仓库行需要支持无凭据、账号密码、API Key 三种模式，并保留仓库 ID、地址、默认分支。
   - 保存逻辑和契约检查要同步更新，避免新增字段被整块配置保存时抹掉。

5. Agent 作用域
   - 逻辑 Agent 可建在组织下，也可建在项目下。组织级 Agent 可被该组织内项目调配，项目级 Agent 只服务所属项目。
   - 组织级 Agent 创建的后端判权必须按组织作用域判断，不能误判到默认控制面项目。
   - 组织 Agent 页展示组织级 Agent 档案和全组织节点，项目 Agent 页展示“可调配 Agent 档案”与项目节点、注册脚本。

6. 执行监控与任务详情
   - 项目监控页增加任务组维度总览，能一眼看到每个任务组的进度、活跃派发、活跃会话、最近事件、关闭阻塞。
   - 任务组工作项详情补齐执行时间线，把会话、派发、模型决策和实时事件串起来，按时间倒序展示。
   - 用户默认看概要，点进任务组和工作项时能看到涉及哪些 Agent、角色、模型、规则和执行结果。

7. 规则编辑体验
   - 规则内容输入区域过窄过小，改为撑满内容区并支持更高的默认编辑高度。
   - 表单应保持密集但不堆砌，规则和仓库配置要有清晰分组。

## 实施约束

- 继续遵守 AI-native 原则：后台管理和入口总控允许人工控制，其余执行链路由系统、总控、监测角色和 Agent 自动完成。
- 服务端 MCP、Skill 同步、调度与事件回送继续集中运行在系统服务器；Agent 端保持轻量注册、自检、领活、执行和回送。
- 不引入固定模型 profile 表；派发时仍由 integration owner 按任务内容显式指定 `model`、`reasoning`、`modelDecision`。
- 文件产出继续落到项目 Git 仓库，不新增独立文件管理系统。
- 高并发场景继续依赖现有按项目过滤、账本截断、项目事件分片和实时事件流；本轮只做边界、表单和可视化补强，不扩大轮询载荷。

## 本轮完成判据

- 系统菜单不再暴露日常账号/Agent/项目混合管理入口。
- 组织成员页能直接看见子账户项目/任务组权限矩阵。
- 项目成员页能授予并展示任务组级权限。
- 项目仓库配置支持账号密码/API Key 模式，界面和保存 payload 一致。
- 组织级/项目级逻辑 Agent 均有清晰管理入口，后端按正确作用域判权。
- 监控页有任务组维度执行总览，任务组详情有工作项执行时间线。
- 契约检查、行为检查和核心测试通过后提交并推送。
