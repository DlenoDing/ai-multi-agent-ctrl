# 第三十九轮管理界面与 Agent 节点治理复验

## 复验范围

本轮继续按普通中文用户的阅读和管理路径复验系统管理、组织管理、项目管理、任务组、执行监控、人工审核、人工指令、项目设置和 Agent 管理。重点检查用户从“项目管理”进入“AI 智能体”后，是否能完整理解 agent 注册、节点查看、异常处置、执行监控和服务端控制之间的关系。

## 发现的问题

### P1：项目 AI 智能体页注册后缺少节点处置流程

项目“AI 智能体”页已经有“项目智能体总览”“项目智能体操作看板”“Agent 注册流程”“Agent 接入与运行闭环”“项目智能体节点”和“注册 agent”。注册脚本来源、集中 MCP、Skill 工作集、实时回送等关键边界已经说明清楚。

但从普通用户视角看，注册完成后仍会直接进入节点表。节点表展示“刷新自检、暂停、恢复、关停、吊销、立即切断”等按钮，功能齐全，但缺少一条按问题场景组织的节点处置路径：

- 节点离线时，用户需要知道先恢复 agent 主机 / Runtime / 心跳，而不是直接重新注册。
- 执行器、远程 MCP、文件系统或 Git 能力修好后，用户需要知道“刷新自检”的作用。
- 运行中异常需要先去执行监控看实时事件和控制 ACK，再决定暂停、恢复、关停或吊销。
- 吊销和立即切断是凭据级高影响动作，需要明确它们会影响 node token 和 MCP grant。

### P2：项目级 Agent 管理需要补一条“查看与处置”闭环

前几轮已经补齐了“注册脚本哪里来”和“agent 端不运行本地 MCP”的边界，但项目负责人日常更多做的是看节点、看异常、看任务、下控制。缺少图形化流程时，用户虽然能看到所有按钮，但需要自己推导每个按钮对应什么场景。

影响：

- Agent 管理页仍有从“安装入口”到“运行管理入口”的断层。
- 节点异常时容易跳过执行监控，直接做高影响控制。
- 对“刷新自检”和“重新注册”的边界理解不够直观。

### P3：优化必须保持简单、稳定和高性能

本轮只新增项目 AI 智能体页的纯前端流程面板和行为门，不新增接口、轮询、状态集合、数据库字段或后端写路径。所有指标复用已下发状态，所有跳转复用现有 `data-jump-panel` 和 `data-menu`。

### P4：项目概览的仓库产出归属缺少归纳层

项目概览底部已经保留“仓库产出归属”明细表，但真实运行态里同一任务组、同一仓库、同一分支和同一允许路径会出现多条历史记录。明细是必要的，不能删；但普通用户需要先知道项目当前涉及几个仓库、多少条仍是有效租约、多少条已被替代、允许路径有几组，然后再决定是否展开读明细。

影响：

- 页面底部容易变成重复行堆叠，阅读成本高。
- 用户要自己从明细表里统计有效租约和被替代记录。
- “多仓库时由总控决定落哪个仓库”的结果缺少一个项目级概览入口。

## 改进方案

1. 在项目“AI 智能体”页新增“Agent 节点处置流程”，放在“Agent 接入与运行闭环”之后、“项目智能体节点”之前。
2. 节点处置流程包含：派发可用性、离线恢复、刷新自检、运行监控、暂停恢复、吊销切断。
3. 明确刷新自检用于重新探测模型执行器、远程 MCP、文件系统和 Git 能力；不是重新签发 join token。
4. 明确运行中异常先回“执行监控”看实时事件和控制 ACK，再做节点控制。
5. 明确吊销或立即切断会废止 node token 和 MCP grant，属于高影响动作。
6. 补充控制台行为门，固定页面顺序、关键边界文案和监控/节点跳转入口。
7. 在项目概览新增“仓库产出归属概览”，放在“最新执行事件”之后、“仓库产出归属”明细表之前。
8. 仓库概览只做已下发数据的前端归纳：仓库数、有效租约、已替代、允许路径组、明细入口，不隐藏原明细表。
