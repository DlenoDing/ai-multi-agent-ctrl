# 第三十六轮管理界面与配置生效流程复验

## 复验范围

本轮继续按普通中文管理员和项目负责人的使用路径复验配置型页面：系统设置、项目设置、模型能力、技能源、角色 Skill 定制、Agent 注册入口、任务组和执行监控。前几轮已经补强 Agent 注册、任务组、人审、人工指令、成员授权等操作入口，本轮重点检查“配置项如何生效”是否足够清晰。

## 发现的问题

### P1：项目设置页缺少配置生效路径

项目设置页已经有“项目设置总览”“项目设置操作看板”和“项目设置职责分区”，但这些面板主要说明本页包含哪些配置。普通项目负责人仍需要自己推导：仓库、基线、默认角色、角色 Skill、系统规则和业务规则，最终如何进入任务组、派发、Agent Runtime 和执行监控。

影响：

- 用户知道在哪里改配置，但不一定知道哪些配置影响后续派发、哪些配置需要回任务组覆盖。
- Agent 注册入口已经独立到项目 AI 智能体页，但项目设置页仍需要说明配置生效后要到任务组和监控页确认结果。
- 角色 Skill 定制是项目和任务组级覆盖，缺少一条从“项目设置”到“任务组详情”的显性路径。

### P2：系统设置页缺少全局能力治理路径

系统设置页已经显示运行参数、技能源、模型能力、角色技能叠加、指令压缩指标和共享定义归属，但这些仍偏长表。系统管理员需要一张图明确：系统设置只治理全局能力，不签发项目 Agent 脚本；项目级注册、角色定制、任务组覆盖和运行监控必须回到项目空间处理。

影响：

- 系统管理员可能把系统设置误解成项目 Agent 注册或项目 Skill 定制入口。
- 模型能力、技能源、角色叠加、指令压缩、共享定义这些对象之间的治理关系不够直观。
- 出现不可用模型或 stale 技能源时，用户知道指标异常，但不一定知道后续应回哪个模块确认项目执行是否恢复。

### P3：优化必须保持轻量

两个配置页面都不应新增接口、轮询或后端状态。新增说明应只使用已加载数据和现有跳转机制，避免增加高并发下的服务端压力。

## 改进方案

1. 项目设置页新增“项目配置生效流程”图形化面板，放在“项目设置职责分区”之后、“项目基础配置”之前。
2. 项目配置流程用六张卡片串联：产出落点、角色 Skill、规则生效、创建任务组、Agent 执行、监控回看。
3. 系统设置页新增“系统能力治理流程”图形化面板，放在“系统设置操作看板”之后、“运行参数（只读）”之前。
4. 系统能力流程用六张卡片串联：运行参数、技能源同步、模型能力、角色叠加追踪、项目级定制/注册、共享定义与压缩。
5. 两个面板只复用当前页面已加载计数和现有 `data-jump-panel` / `data-menu` 跳转，不新增 API 和轮询。
6. 补充行为门，断言两个页面必须先显示总览、看板、流程，再进入长表和表单，并覆盖 Agent 注册、项目设置、任务组、执行监控、Skill、模型、MCP 的边界提示。
